# SprintPath - アジャイル開発フレームワーク

## 概要

**SprintPath**は、Issue駆動開発、継続的品質保証、AI Agentとの協働を統合した実践的なアジャイル開発フレームワークです。スクラムをベースに、現代の開発環境に最適化されています。

---

## 5つの原則

> **警告**: 原則違反は `.factory/memory/violations.md` に記録される。
> 繰り返しの違反は許容されない。

### 1. 🎯 Issue-First (イシュー起点) [最重要]
> **「コードを書く前に、必ずIssueを確認する」**

すべての作業はGitHub Issueから始まる。**Issueなしの作業は存在しない。**

**実践:**
- 作業開始前に `gh issue list` でIssueを確認
- Issueがなければ**必ず**作成してから着手
- 受け入れ基準を明確にする

**違反例（許容されない）:**
- ユーザー指示に即座に対応し、Issue確認を省略
- 「軽微な変更」としてIssue化せずに実装
- 会話の流れで決まった機能をそのまま実装

**正しい対応:**
```
ユーザー: 「〜を実装してください」
Droid: 「対応するIssueを確認します」
       → gh issue list で確認
       → Issueなし: 「Issueを作成してから対応しますか？」
       → Issueあり: Issue番号を記録して作業開始
```

### 2. 🔄 Continuous Quality (継続的品質)
> **「テストが通らなければ、コミットしない」**

品質は後付けではなく、開発プロセスに組み込む。

**実践:**
- 実装後は必ずテスト・型チェック・リントを実行
- 全てパスするまでコミットしない
- CI/CDでの自動検証

### 3. 👤 Clear Ownership (明確な責任)
> **「役割分担を明確にし、責任者を決める」**

誰が何を担当するかを明確にし、責任の曖昧さを排除する。

**実践:**
- タスクには必ず担当者をアサイン
- AI Agentは実行者、人間は意思決定者
- レビュー・承認フローを明確化

### 4. 📊 Visibility (可視化)
> **「進捗は常に見える状態にする」**

暗黙知を形式知に変換し、チーム全体で状況を共有する。

**実践:**
- ラベル、ステータスで進捗を可視化
- ドキュメントを最新に保つ
- 完了報告を必ず行う

### 5. 🚀 Ship Small (小さく出荷)
> **「大きな変更より、小さな改善を積み重ねる」**

1つのPRは1つの目的。大きな機能は分割してリリースする。

**実践:**
- PRは小さく保つ（目安: 200行以下）
- 機能フラグで段階的リリース
- 頻繁にmainにマージ

## 開発サイクル

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    │
│    │  PLAN    │───▶│  BUILD   │───▶│  CHECK   │───▶│  SHIP    │    │
│    │ 計画     │    │ 実装     │    │ 検証     │    │ 出荷     │    │
│    └──────────┘    └──────────┘    └──────────┘    └──────────┘    │
│         │                                               │           │
│         └───────────────◀───────────────────────────────┘           │
│                         LEARN (学習)                                │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### PLAN (計画)
- Issue確認・作成
- 受け入れ基準の定義
- 優先度・見積もりの設定
- 担当者のアサイン

### BUILD (実装)
- コーディング
- ユニットテスト作成
- ドキュメント更新

### CHECK (検証)
- 全テスト実行
- 型チェック
- リントチェック
- コードレビュー

### SHIP (出荷)
- コミット
- プッシュ（承認後）
- 完了報告

### LEARN (学習)
- レトロスペクティブ
- プロセス改善
- ナレッジ蓄積

## 開発フロー (5ステップ)

```
STEP 1: CONFIRM (確認)
   │
   ├─ gh issue list --state open
   ├─ 優先度確認
   └─ Issueなし → 作成または確認
   │
   ▼
STEP 2: IMPLEMENT (実装)
   │
   ├─ コーディングルール遵守
   ├─ テスト作成
   └─ ファイル配置規則
   │
   ▼
STEP 3: VERIFY (検証)
   │
   ├─ bun run test
   ├─ bun run typecheck
   └─ bun run lint
   │
   ▼
STEP 4: COMMIT (コミット)
   │
   ├─ コミットメッセージ形式
   └─ Refs #ISSUE_NUMBER
   │
   ▼
STEP 5: REPORT (報告)
   │
   ├─ 実装内容
   ├─ 変更ファイル
   ├─ テスト結果
   └─ コミットハッシュ
```

## ラベル体系

### 優先度 (Priority)
| ラベル | 説明 | SLA |
|--------|------|-----|
| `priority: critical` | 本番障害、セキュリティ | 24時間 |
| `priority: high` | 重要機能、ブロッカー | 3日 |
| `priority: medium` | 通常機能 | 1週間 |
| `priority: low` | 改善、nice-to-have | 将来 |

### タイプ (Type)
| ラベル | 説明 |
|--------|------|
| `type: feature` | 新機能 |
| `type: bug` | バグ修正 |
| `type: tech-debt` | 技術的負債 |
| `type: test` | テスト追加 |
| `type: spike` | 調査・研究 |

### 見積もり (Story Points)
| ラベル | 目安時間 |
|--------|---------|
| `story-points: 1` | ~2時間 |
| `story-points: 2` | ~4時間 |
| `story-points: 3` | ~1日 |
| `story-points: 5` | ~2-3日 |
| `story-points: 8` | ~1週間 |

### ステータス (Status)
| ラベル | 説明 |
|--------|------|
| `status: backlog` | バックログ内 |
| `status: ready` | 実装準備完了 |
| `status: in-progress` | 実装中 |
| `status: review` | レビュー中 |
| `status: blocked` | ブロック中 |

### エリア (Area)
| ラベル | 説明 |
|--------|------|
| `area: frontend` | UI/UX |
| `area: backend` | API/ビジネスロジック |
| `area: database` | DB/スキーマ |
| `area: devops` | CI/CD/インフラ |
| `area: ai` | AI/ML |

## 品質ゲート

### コミット前チェック (必須)
```bash
bun run test        # 全テストパス
bun run typecheck   # 型エラーなし
bun run lint        # リントエラーなし
```

### プッシュ前チェック (推奨)
- 変更ファイルのレビュー
- セキュリティ確認（秘密情報なし）
- ドキュメント更新確認

## メトリクス

| 指標 | 目標 | 説明 |
|------|------|------|
| テストカバレッジ | 70%+ | ユニットテストのカバレッジ |
| リードタイム | <5日 | Issue作成からクローズまで |
| バグ率 | <10% | リリース後のバグ発生率 |
| PR サイズ | <200行 | 変更行数の目安 |

## セレモニー

### デイリー (任意)
- 時間: 10分
- 内容: 進捗確認、ブロッカー共有

### ウィークリー
- 時間: 1時間
- 内容: バックログリファインメント、優先度調整

### スプリント (2週間)
- プランニング: 2時間
- レビュー: 1時間
- レトロスペクティブ: 1時間

## AI Agent (Droid) との協働

### 役割分担

| 役割 | 人間 | AI Agent |
|------|------|----------|
| 要件定義 | ✅ 決定 | 提案・整理 |
| 設計判断 | ✅ 決定 | 提案・実装 |
| 実装 | レビュー | ✅ 実行 |
| テスト | 確認 | ✅ 実行 |
| コミット | 承認 | ✅ 実行 |
| プッシュ | ✅ 承認 | 実行 |

### AI Agent開発フロー

```
CONFIRM → IMPLEMENT → VERIFY → COMMIT → REPORT
```

1. **CONFIRM**: Issueを確認、なければ人間に確認
2. **IMPLEMENT**: コーディングルールに従って実装
3. **VERIFY**: test, typecheck, lint を実行
4. **COMMIT**: 規約に従ってコミット
5. **REPORT**: 完了内容を報告
